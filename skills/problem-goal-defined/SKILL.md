# 问题定义与目标拆解

当用户带着模糊的问题或宏大的目标来找你时，用本 Skill 引导他们完成从"混沌"到"清晰可执行"的思维转化。

## 判断工作模式

用户输入后，先判断需要哪种模式：

| 模式 | 触发信号 | 核心产出 |
|------|----------|----------|
| **问题定义** | 用户描述了一个困惑、痛点、瓶颈、现象 | 精确定义的问题陈述 + 根因分析 |
| **目标拆解** | 用户提出了一个目标、愿景、计划、KPI | WBS/OKR + 优先级排序 + 里程碑 |
| **全链路** | 用户既有模糊问题又有目标，或问题定义后自然需要拆解 | 先定义 → 再拆解，完整闭环 |

判断后向用户确认，然后进入对应工作流。

---

## 模式一：问题定义工作流

核心哲学：**穿透表象，直抵根因。** 用户最初描述的大概率是症状，不是问题本身。

### 第一步：问题澄清 — 回归事实

用 5W2H 框架向用户提问，把模糊的"感觉不对"变成客观描述：

```
What  — 具体发生了什么？（要求用事实和数据描述，不用"我觉得"）
Why   — 你认为为什么会发生？（初步假设，后面要验证）
Who   — 涉及哪些人/团队/利益相关者？
When  — 什么时候开始的？是持续性的还是间歇性的？
Where — 在什么场景/环节/地点发生？
How   — 具体表现是什么？
How much — 影响有多大？（量化：金额、时间、数量、百分比）
```

关键原则：
- 用"我观察到…"句式引导用户区分**事实**和**观点**
- "上季度客户投诉增长了30%"是事实；"客服态度不好"是观点
- 信息不足时主动向用户索要数据或要求补充场景

### 第二步：根因挖掘 — 5 Whys

对识别出的表象连续追问"为什么"，直到触及可操作的根因：

```
表象 → Why? → 中间原因1 → Why? → 中间原因2 → Why? → ... → 根因
```

典型追问 3-5 层。停止条件：到达一个可以通过改变制度/流程/策略来解决的层面。

示例（丰田经典）：
```
地上有油 → 机器漏油 → 垫圈老化 → 采购了劣质垫圈 → 采购KPI只看最低价格 → 采购部门考核指标设计不合理
```

如果问题涉及多个因素，画**逻辑树**（MECE原则：互不重叠，完全穷尽）。

### 第三步：边界分析 — 划定作战范围

明确三个边界：
1. **系统边界**：哪些因素在内部（可控）？哪些在外部（只能适应）？
2. **利益相关者边界**：涉及谁？各自的立场和诉求是什么？
3. **时间边界**：关注的时间窗口？解决的窗口期？

同时识别：
- **关键变量**：对结果影响最大的"旋钮"有哪些？
- **约束条件**：预算、时间、人力、法规等硬限制

### 第四步：重新框定问题

将分析结果凝练为一句高质量的问题陈述，使用模板：

> "对于 **[谁/哪个群体]** 来说，**[什么情况/根因]** 导致了 **[什么问题/障碍]**，其可量化的影响是 **[具体数字]**。我们该如何 **[解决方向]**？"

框定检查清单：
- [ ] 是否指向根因，而非表象？
- [ ] 是否包含量化数据？
- [ ] 是否明确了利益相关者？
- [ ] 是否留有多个解决方案的空间？（不应预设唯一答案）

### 第五步：假设检验

列出问题定义依赖的底层假设，针对最关键且最不确定的假设，建议最小化验证实验。

## 模式二：目标拆解工作流

核心哲学：**从愿景到行动，每一层都必须可执行。**

### 第一步：锚定总目标（SMART 检验）

将用户的目标用 SMART 原则打磨：

```
S - Specific    具体：目标清晰明确，不含糊
M - Measurable  可衡量：有量化指标衡量是否达成
A - Achievable  可达成：有挑战性但现实可行
R - Relevant    相关：与上级目标/整体战略对齐
T - Time-bound  有时限：有明确的截止日期
```

如果用户的目标不满足 SMART，帮其逐项补全。

### 第二步：逆向推导 + 正向验证

**逆向推导**：从总目标反向追问 —— "要达成这个目标，必须先完成哪几件关键事情？"

**正向验证**：将推导出的子目标组合起来，检查是否充分且必要地支撑总目标（WBS 100% 原则：所有子任务的工作量总和 = 父任务工作量）。

### 第三步：选择拆解维度

根据目标性质选择合适的拆解维度（可组合使用）：

| 维度 | 适用场景 | 示例 |
|------|----------|------|
| 按时间 | 有清晰节奏的项目 | 年度→季度→月度→周 |
| 按功能/模块 | 产品或系统开发 | 用户模块、交易模块、客服模块 |
| 按交付物 | 成果导向的项目 | 大纲→草稿→校对版→终稿 |
| 按组织/资源 | 跨部门协作 | 市场部、研发部、运营部 |
| 按风险/依赖 | 高风险或强依赖项目 | 先攻克技术风险最高的部分 |

### 第四步：构建层级结构（WBS）

将目标逐层分解为：目标 → 子目标 → 任务 → 行动步骤

每个最底层行动步骤必须明确：
- **谁**（Who）来做
- **做什么**（What）
- **何时完成**（When）
- **需要什么资源**（Resource）
- **完成标准**（Standard）

### 第五步：优先级排序

根据场景选择排序框架：

**艾森豪威尔矩阵**（快速分类）：
- 重要且紧急 → 立即做
- 重要不紧急 → 计划做（战略价值所在）
- 紧急不重要 → 授权/自动化
- 不重要不紧急 → 不做

**价值-成本矩阵**（项目场景）：
- 高价值低成本 → Quick Wins，优先执行
- 高价值高成本 → 战略性投入，仔细规划
- 低价值低成本 → 填充项，资源空闲时做
- 低价值高成本 → 坚决不做

**MoSCoW 法**（敏捷/产品场景）：
Must have → Should have → Could have → Won't have

### 第六步：识别依赖与关键路径

- 画出任务间的依赖关系（串行 vs 并行）
- 识别关键路径：决定总工期的最长任务链
- 标记可并行的任务组，压缩总工期

### 第七步：设定里程碑

在关键节点设置检查点：
- 建议每完成 20-30% 工作量设一个里程碑
- 里程碑既是进度检查点，也是阶段性庆祝点

### 第八步：风险与 Plan B

- 为关键路径和高风险任务识别潜在风险
- 准备替代方案（Plan B）
- 评估资源瓶颈，必要时做资源平衡

## 模式三：全链路（问题定义 → 目标拆解）

两者的协同逻辑：

```
问题定义 → 确定"做什么"和"为什么做"
    ↓ 提供靶心和约束
目标拆解 → 规划"怎么做"和"何时做"
    ↓ 执行中遇到新发现
反馈修正 → 返回问题定义，重新框定
```

执行顺序：
1. 先完成问题定义工作流（第一步到第五步）
2. 将精确定义的问题转化为目标（用 OKR 或 SMART）
3. 进入目标拆解工作流（第一步到第八步）
4. 标注反馈环：执行中发现新问题时，回到问题定义

## 输出格式

### 问题定义产出模板

```markdown
## 问题定义报告

### 1. 问题陈述
"对于[谁]来说，[根因]导致了[问题]，其影响是[量化数据]。"

### 2. 根因分析
[5 Whys 链条或逻辑树]

### 3. 边界与约束
- 系统边界：内部可控因素 / 外部环境因素
- 利益相关者：[列表及各自立场]
- 时间边界：[窗口期]
- 关键变量：[影响最大的旋钮]
- 硬约束：[预算/时间/法规等]

### 4. 底层假设
[列出关键假设及验证建议]

### 5. 建议的解决方向
[2-3 个可选方向，不预设唯一答案]
```

### 目标拆解产出模板

```markdown
## 目标拆解路线图

### 总目标（OKR / SMART）
O: [方向性目标]
KR1: [可衡量的关键结果]
KR2: ...
KR3: ...

### WBS 分解
1.0 [子目标A]
  1.1 [任务] → 行动步骤（Who/What/When）
  1.2 [任务] → ...
2.0 [子目标B]
  ...

### 优先级排序
[按所选框架排序结果]

### 依赖关系与关键路径
[串行/并行关系，关键路径标注]

### 里程碑计划
M1 (日期): [交付物]
M2 (日期): [交付物]
...

### 风险与 Plan B
[关键风险及替代方案]
```

## 执行要点

1. **不要一次倒出所有框架**：根据用户问题的性质，选择最合适的 2-3 个框架深入，其余一笔带过
2. **追问比回答更重要**：问题定义阶段，你的核心价值是提出好问题，而非急于给答案
3. **量化一切**：每个环节都要求数据，用户说"很多"就追问"具体是多少"
4. **警惕确认偏误**：如果用户一开始就预设了原因，刻意引导他们考虑反面证据
5. **区分问题空间和方案空间**：在问题充分定义之前，不要跳入解决方案
6. **产出要可执行**：最底层的行动步骤必须明确到"谁在什么时候做什么"
